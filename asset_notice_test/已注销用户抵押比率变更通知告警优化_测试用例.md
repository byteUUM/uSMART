# 已注销用户股票抵押比率变更通知告警优化 测试用例

> 需求：USSGZT-9963　项目：`asset-center-sg`　分支：`feature-260821-删除告警日志`（SIT 分支 `SIT-20250707`）
>
> 改动本质：**告警降噪**。「查不到用户」的分支由「打日志 + 发企业微信告警群」改为「只打日志」。
> 功能行为不变，所以验证分两半：**降噪生效** + **正常通知没被改坏**。

### 0.1 测试数据 A 的三种拿法（按省事程度排序）

**路子 A：捞现成数据（推荐）**

历史遗留问题，SIT 库很可能已有这类脏数据。让开发/DBA 跑一句（表名以实际为准）：

```sql
SELECT p.user_id, p.symbol, p.qty
FROM 碎股持仓表 p
LEFT JOIN 用户表 u ON p.user_id = u.user_id
WHERE u.user_id IS NULL OR u.status = <已注销状态值>;
```

**路子 B：自己造**

给测试账户建一笔碎股持仓，再把用户置为已注销。
★ 先确认「查不到用户」是记录不存在还是状态过滤导致（见 explain.txt 待确认第 1 项），否则走不到目标分支。

**路子 C：让开发直接构造 notice**

由开发往 MQ 投一条 `userId` 为不存在值的 notice，或临时开内部接口触发。
本次验的是告警降噪，不是通知业务本身，这条路完全够用，且最快。

## 1. 核心场景：已注销用户

### NTC-01　已注销用户 + 抵押比率变更（P0）

**操作步骤**

1. 记录当前时间（精确到分钟），后面查日志、对告警群都要用
2. 进入 `保证金比率管理` → tab `股票抵押比率变更`，点「添加」
3. 股票代码填数据 A 的 `symbol`，市场选对
4. 「变更后抵押比率」填一个**与变更前不同**的值（如 0.5 → 0.4，注意是小数不是百分数）
5. 「变更生效时间」设为**当前时间 + 3~5 分钟**
6. 确认提交，刷列表等「生效状态」变成 `SUCCESS`
7. 查日志 + 盯告警群

> ★ 别用 tab `保证金设置` / `IB保证金`（多头/空头初始、维持保证金率）—— 那是保证金
> 那一套，改它不会触发本次的抵押比率变更通知。
>
> ★ 「生效状态 = SUCCESS」是关键信号，证明变更确实执行了。此时若日志搜不到 warn，
> 说明是真问题，不是"没触发"。

**预期结果**

| # | 检查项 | 期望 |
| --- | --- | --- |
| 1 | 服务日志 | 搜到 `用户ID[<userId>]没有找到用户，请检查` |
| 2 | 日志级别 | `WARN`（日志行第 3 个字段） |
| 3 | 企业微信告警群 | **该 userId 相关告警一条都没有** |
| 4 | 邮件 | 已注销用户不应收到邮件（本来也发不出去） |
| 5 | 无异常 | 无 NPE / 500 / 消息消费失败，任务正常跑完后续用户 |

### NTC-02　多个已注销用户批量（P1）

**操作步骤**：改一个被多个已注销用户持有的标的的抵押比率

**预期结果**

- 每个已注销 userId 各打一条 warn 日志
- 告警群零消息
- 循环 `continue` 后**继续处理后面的用户**，不会因为前面某个用户查不到就中断整批（重点，别漏）

### NTC-03　已注销与正常用户混合（P0）

**操作步骤**：改一个同时被「已注销用户」和「正常用户」持有的标的的抵押比率

**预期结果**

- 已注销用户：打 warn 日志，不告警
- 正常用户：**正常收到抵押比率变更邮件**
- 两者互不影响

> 这条是全套用例里最有价值的一条，一次同时覆盖降噪和回归。

## 2. 回归：正常通知链路没被改坏（P0）

### REG-01　正常用户抵押比率变更通知

**操作步骤**：用数据 B（正常用户）执行同样的抵押比率变更

**预期结果**

- 正常收到抵押比率变更邮件，内容（标的、原比率、新比率）正确
- 日志中**不出现** `没有找到用户`
- 改动前后邮件内容一致

> 降噪类改动最典型的事故：删告警时误伤了正常发送逻辑，导致上线后没人收到通知邮件。
> 这条必测，不能因为「需求说只删告警」就跳过。

### REG-02　超过有效期分支仍然告警

**操作步骤**：制造一条超过 `WARNING_LIMIT_MINUTES` 的通知。可尝试把「变更生效时间」
设为一个**已经过去**的时间点（或改通知创建时间 / 让开发协助构造），使定时任务处理时
已超出有效期窗口。

**预期结果**

- 日志出现 `跳过不应该向用户发送的通知`
- **告警群仍然收到**「跳过发送孖展比率通知，通知可能已经超过有效期」
- 这个分支的 `sendTxtMessage` 本次**没有**被删，保持原行为

### REG-03　其他类型告警未受影响

**操作步骤**：触发 asset-center-sg 其他会告警的异常场景

**预期结果**：其他告警照常进群，本次改动只影响「查不到用户」这一处

## 3. 日志查询方法

### 3.1 Kibana / 日志平台

服务选 `asset-center-sg`，环境 `sit`，时间范围卡在操作的那几分钟。

```
# 核心验证点
message: "没有找到用户，请检查"

# 带 userId 精确定位
message: "没有找到用户，请检查" and message: "<你的userId>"

# 反查：这个 userId 走了哪些分支
message: "<你的userId>" and message: "通知"

# 另一个分支（超有效期），确认告警群消息来源
message: "跳过不应该向用户发送的通知"
```

### 3.2 服务器 / 容器内

```bash
grep -n "没有找到用户，请检查" /apps/logs/asset-center-sg/*.log
grep -n "跳过不应该向用户发送的通知" /apps/logs/asset-center-sg/*.log
```

### 3.3 日志字段对照

```
2026-08-19 08:34:27,556 | sit | WARN | asset-center-sg | ... | [traceId] | ... | 用户ID[xxx]没有找到用户，请检查
      时间                 环境    级别      服务名                                        内容
```

拿到 traceId 后可用它串起整条链路，看这条 notice 从哪来、后续怎么走的。

## 4. 通过标准

全部满足才算通过：

1. NTC-01 / NTC-03 中，已注销用户有 WARN 日志、**告警群无消息**
2. REG-01 中，正常用户**照常收到邮件**，功能未被破坏
3. REG-02 中，超有效期分支**仍然告警**（该分支未在本次范围内）
4. 全程无 NPE / 消息消费失败 / 任务中断

## 5. 已知风险 / 关注点

1. **假通过风险**：如果造数据方式不对（比如只改了状态但代码是按记录存在性判断），根本走不到目标分支，日志搜不到，告警群自然也没消息 —— 这时「告警群无消息」是假象。**必须先在日志里搜到那条 warn，才能证明分支被执行过**。
2. **回归缺失风险**：只验降噪不验正常通知，是这类改动最容易漏的地方。
3. **日志级别**：SIT 若把日志级别设在 ERROR，`log.warn` 搜不到，会误判为改动未生效。测前先确认。
4. **环境版本**：先确认 SIT 部的是目标分支，否则整轮白测。
